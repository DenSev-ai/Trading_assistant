# Trading assistant — SPEC v3.0

Читай вместе с `docs/CONTRACTS.md` и файлом текущего шага `docs/steps/STEP_N.md`. Других документов не читай (`docs/DECISIONS.md` — архив, не загружать).

## 1. Цель
Сервис для российского фондового рынка: собирает новости → отбирает по ключевым словам → кластеризует похожие → анализирует двумя разными LLM (OpenRouter) → делает прогноз, только если модели согласны по тикеру и направлению, обе ожидают движение цены не менее 15% за срок не более 180 дней, а их оценки величины расходятся не более чем на 20% → шлёт в Telegram → проверяет прогноз по ценам MOEX ISS → считает, какой процент прогнозов сбылся. Принцип: лучше меньше прогнозов, но точнее; число прогнозов не цель.

**Что такое «сбылся»:** цена достигла движения ≥ 15% в предсказанную сторону хотя бы на одном закрытии в пределах срока (даже если потом вернулась). Подробно — CONTRACTS §6.
**Критерий успеха проекта:** у боевой пары (`consensus`) не менее 75% сбывшихся прогнозов при n ≥ 100 выданных и проверенных прогнозов (`evaluation.min_success_pct`, `evaluation.sample_n`; пользователь может менять).
**Вторая цель (после признания проекта пригодным):** найти модели с лучшим отношением «стоимость вызовов, давших выданные прогнозы ÷ процент сбывшихся». Каждая модель оценивается отдельно; модель с долей сбывшихся < 75% отбрасывается, какой бы дешёвой ни была. Порядок: сначала сильная платная пара (уровень не выше `anthropic/claude-sonnet-5.5`, два разных разработчика), потом тесты более слабых и дешёвых моделей. Смену пары делает только пользователь (сервис лишь предлагает). Подробно — CONTRACTS §9.
**Отчёты:** ежедневная сводка, еженедельный отчёт и событийные письма на e-mail работают с первого запуска (CONTRACTS §10).

## 2. Стек и среда
- Python 3.12, Windows 10, ноутбук i3 / 6 ГБ ОЗУ. Запуск: `python -m trading_assistant` из корня репозитория.
- Библиотеки (версии в `requirements.txt`): aiosqlite, httpx, feedparser, aiogram 3, aiosmtplib, rapidfuzz, pydantic, pydantic-settings, pyyaml, tzdata, pytest, pytest-asyncio, ruff. Других не добавлять.
- Всё на asyncio. `feedparser.parse` вызывать только через `asyncio.to_thread`.
- Время: хранение в UTC (ISO 8601, `YYYY-MM-DDTHH:MM:SS+00:00`), показ и расписание в `Europe/Moscow`.
- Файлы данных в `data/` (создаётся сервисом): БД `data/trading.db`, логи `data/app.log` и `data/errors.log`, блокировка `data/service.lock`, флаг остановки `data/stop.flag`.
- Секреты только в `.env` (в git не попадает). Остальные настройки в `config/*.yaml|json` (в git).

## 3. Правила кода (обязательные)
1. Делай ТОЛЬКО текущий шаг. Код следующих шагов не пиши. Файлы вне списка шага не меняй. `docs/*` не меняй.
2. Если в SPEC, CONTRACTS и шаге есть противоречие или не хватает данных — остановись и задай один вопрос. Не придумывай.
3. Логика — чистые функции (данные на входе, данные на выходе). Ввод-вывод (сеть, БД, Telegram, время) — в тонких классах-обёртках.
4. Время только через `Clock` (`clock.now()`). `datetime.now()` и `time.sleep()` в логике запрещены (`asyncio.sleep` разрешён).
5. Числа, пороги, URL, имена моделей — только из конфигов. «Магических чисел» в коде нет.
6. Нет блокирующих вызовов в event loop. У каждого сетевого запроса таймаут из конфига.
7. Секреты не логируются и не печатаются (в чек-листе только факт наличия).
8. Типизация публичных функций обязательна; `mypy` не используется.
9. Стиль: PEP 8, `ruff check .` без ошибок, длина строки 100. Имена — английские. Docstring — одна строка по-русски. Тексты для пользователя — русские.
10. Тесты — `pytest`, `asyncio_mode=auto`. HTTP мокается через `httpx.MockTransport`, БД — `:memory:`, время — `FakeClock`. Живые вызовы только в тестах с маркером `@pytest.mark.live` (по умолчанию пропускаются).
11. Шаг готов, когда `pytest` и `ruff check .` проходят без ошибок. В конце ответа 3 строки: что сделано / как запустить / что не сделано. Затем фраза: `Шаг N готов. Жду подтверждения.`

## 5. Конвейер (один цикл `Pipeline.run_cycle`)
1. **collect** — читает RSS всех включённых источников; берёт записи не старше `news.window_hours`, не более `news.max_items_per_feed` новейших на ленту; дубли по `url` пропускает.
2. **prefilter** — ключевые слова по заголовку + описанию. Нет совпадения → статус `filtered`.
3. **fulltext** — полный текст (способ в `sources[].fulltext`: `page` или `rss`). Короче `news.min_fulltext_chars` → `no_fulltext`. Страницы качаются с учётом `robots.txt`.
4. **cluster** — rapidfuzz по заголовкам, окно `news.cluster_window_hours`. Новая статья в существующем кластере: `sources_count` +1 (число уникальных источников), повторный анализ не запускается.
5. **analyze** — кластеры `pending` свежее 24 ч, порядок: `sources_count` по убыванию, затем новее. Две модели пары параллельно; кандидаты — только в состоянии `candidates_test` (CONTRACTS §4, §9). Ретраи и бюджет: CONTRACTS §4.
6. **consensus** — CONTRACTS §5. Сохраняет `predictions` для каждой модели (с флагом `is_issued`) и `consensus`.
7. **base price** — сразу после сохранения запрашивает последнюю цену MOEX и пишет в `base_price`.
8. **backtest** — проверка прогнозов (CONTRACTS §6), не чаще `polling.backtest_interval_sec`; затем `evaluation.update` (тесты и вердикты, CONTRACTS §9).
9. **dispatch** (Шаг 5) — алерты и дайджест.
10. **reports** (подшаг 4D) — e-mail отчёты (CONTRACTS §10).

Статусы статьи: `filtered | no_fulltext | clustered`. Статусы кластера: `pending | analyzed | failed | skipped`.
Ошибка одного этапа или источника логируется и не останавливает цикл.

## 6. Расписание (МСК)
- `[00:00, 09:45)` — PASSIVE: собирает и анализирует, алерты не шлёт (копятся для дайджеста).
- `[09:45, 22:40)` — ACTIVE: алерты уходят сразу. В 09:45 — дайджест накопленного.
- `[22:40, 24:00)` — STOPPED: сервис завершает работу сам.
- Запуск вне Python: Планировщик Windows в 07:45 пн–пт с пробуждением ПК (`scripts/install_task.ps1`). В выходные и даты из `schedule.non_working_dates` сервис завершается сразу (флаг `--force` отключает проверку).
- Старт позже 09:45 и дайджест за сегодня не отправлялся → отправить при первом цикле ACTIVE. Записи старше 24 ч в дайджест не идут.
- Окно сбора новостей всегда 24 ч. Спец-догона нет.
- Пока сервис работает, сон ПК запрещён (`SetThreadExecutionState`, `platform_win.py`); при выходе запрет снимается.
- Один экземпляр: файловая блокировка `data/service.lock`.
- Режимы CLI: `--check-config`, `--dry-run` (не слать в Telegram), `--once` (один цикл и выход, без проверки фазы и рабочего дня), `--report` (печать статистики), `--force`.

## 7. Telegram (Шаг 5)
Получатели — список `TELEGRAM_CHAT_IDS`; остальных игнорировать. Команды: `/start`, `/help`, `/stats [ТИКЕР]`, `/last`, `/status`. Формат сообщений — CONTRACTS §7. Лимит: `telegram.daily_alert_limit` обычных алертов в сутки; приоритетные (> 25% или ≥ 15% за срок < 120 дн.) сверх лимита. Анти-спам: не чаще 1 алерта на тикер за `telegram.antispam_hours` — действует всегда, в том числе для приоритетных. Без Telegram-переменных вместо бота работает `LogNotifier` (пишет в лог). Пауза 1 с между сообщениями; ошибка доставки одному получателю не прерывает остальных; пометка «отправлено» ставится после успешной отправки.

## 10. Допущения и ограничения
- Успех оценивается по факту движения цены, а не по влиянию именно этой новости: на цену могут влиять другие события.
- 100 проверенных прогнозов при условии «≥ 15% за срок до 180 дней» могут накапливаться месяцами; это принято. Пользователь может изменить `evaluation.sample_n`.
- `confidence` — самооценка модели, у разных моделей шкала разная. Это фильтр момента («выдавать/не выдавать»); пригодность модели определяется только фактической долей сбывшихся прогнозов.
- Прогнозы с разными `prompt_version` и разными парами в одну статистику не смешиваются.
- Провайдер LLM можно заменить на другой OpenAI-совместимый (`llm.base_url`, ключ в `.env`).
